# 1. Purpose and Scope

This Relevance Scoring document defines the keyword weighting models, search result ranking formulas, sorting strategies, and search caching/invalidation rules for the search engine of the Pokémon Knowledge Management Platform (PKMP) v1.0.0. These rules ensure relevant search results are returned quickly.

---

# 2. Keyword Weighting Model

The search engine uses PostgreSQL's full-text search relevance functions (`ts_rank` and `ts_rank_cd`) to rank search results.

- **Weight Assignments:**
  - **Weight A (1.0):** Direct string matches on Pokémon species name, move name, or ability name.
  - **Weight B (0.4):** Matches on types, classifications, or ability lists.
  - **Weight C (0.2):** Matches on description columns (e.g., Pokédex flavor text).
- **Density Ranking (`ts_rank_cd`):** Ranks search matches based on the proximity of search terms to each other, improving relevance for multi-word queries.

---

# 3. Sorting and Rank Calculations

Results are sorted based on relevance score and secondary criteria.

- **Sorting Pipeline:**
  1. Primary Sort: Relevance Score (`ts_rank_cd`) in descending order.
  2. Secondary Sort: Matches on exact names are boosted to the top of the results.
  3. Tertiary Sort: Sort by National Pokédex number (`national_num`) in ascending order.
- **Result Caps:** Public search endpoints limit return payloads to 100 entries per request.

---

# 4. Search Caching and Invalidation

To meet the 200 ms response budget under concurrent load (REQ-NFR-101), search queries are cached in Redis.

- **Cache Keys:** Keys are generated by hashing the query parameters:
  `search:cache:query=water_type:gen=3:limit=20`
- **TTL Policies:**
  - **Search Results Cache:** TTL is set to 2 hours (`TTL = 7200`).
  - **Fuzzy Autocomplete suggestions Cache:** TTL is set to 24 hours (`TTL = 86400`).
- **Invalidation Triggers:** When an editor commits changes to a Pokémon, move, or ability record via the CMS, a trigger invalidates the corresponding search cache keys.
